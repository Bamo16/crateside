# Spotting a non-premium queue item from the YouTube API

*Note, 2026-08-13, frozen: the measurement behind [ADR 0016](../adr/0016-the-download-reports-its-own-quality-and-parking-gained-a-reason.md). Names are as they were then; "the Queue view" has since become the Tracks view.*

**Question.** Can crateside warn, from API metadata alone, that a queued URL will not yield a
YouTube Premium download — without shelling out to yt-dlp with cookies?

**Answer: yes, for the positive case, exactly.** Measured, not assumed.

## The signal

`snippet.description` contains **`Auto-generated by YouTube`**. YouTube writes it on every
auto-generated Music art track, alongside a leading `Provided to YouTube by <distributor>`.

`playlistItems.list` already returns the description on the call the Queue view makes anyway,
so **the signal costs no extra quota** — no second request, no yt-dlp.

## What it was measured against

The 552-video corpus in `V:\Repos\Yt-dlp_Formats`, resolved three ways (logged out, signed-in
free, signed-in Premium). All 552 were still live and were re-queried through
`videos.list` (12 quota units).

| signal | fires | false positives | precision | recall |
|---|---:|---:|---:|---:|
| **`Auto-generated by YouTube`** | 326 | **0** | **100%** | 77.6% |
| `Provided to YouTube by` | 326 | 0 | 100% | 77.6% |
| channel title ends `- Topic` | 327 | 1 | 99.7% | 77.6% |
| `contentDetails.licensedContent` | 415 | 34 | 91.8% | 90.7% |
| `categoryId == 10` (Music) | 496 | 88 | 82.3% | 97.1% |
| `topicDetails` mentions music | 517 | 103 | 80.1% | 98.6% |

Two results carry the design:

1. **The marker set is *identical* to yt-dlp's.** The 326 videos it fires on are exactly the
   326 that yt-dlp reports an `artist` for — StemForge's `IsMusicTrackEntity` test. Not
   "correlated with": the symmetric difference is **0**. The API reproduces a signal that was
   assumed to require yt-dlp.
2. **Those 326 were premium 326/326.** No false positives.

## What it cannot do

Of the 226 videos without the marker, **94 (42%) were still premium**. Nothing available in
the API separates them: within that subset, `licensedContent` reaches 62% precision and
`licensedContent + categoryId 10` only 69%.

So the absence of the marker predicts *nothing*, and the UI says so. The flag reads as
"a better URL for this song may exist — worth checking", never as "this will download badly".
Claiming the latter would be wrong two times in five.

## The marker is forgeable, and that is fine

Nothing stops anyone typing `Auto-generated by YouTube` into a description. It is a
**convention YouTube's own tooling writes, not an attestation**, and the corpus was assembled
from real searches rather than adversarially against forgery, so "zero false positives" means
*nobody in this corpus had lied*, not *lying is impossible*.

Worth being clear about the actual stakes: a forged marker means one queued item shows no
warning, gets processed, and downloads at ordinary quality — which the user notices, and which
**StemForge reports accurately at download time anyway** (`PremiumExpectation`, ADR 0013,
which sees the real format ladder). This flag is a *pre-flight hint on metadata*; StemForge
remains the authority on what was actually fetched. Hardening it against forgery would buy
nothing that the authoritative check does not already provide.

Requiring the channel title to *also* end in `- Topic` would raise the forgery bar at no
measured cost in recall (0 videos carry the marker off a Topic channel). It is not done,
because it defends against an attacker nobody has, while adding a second thing to re-measure.

**The one real false positive is not an impostor.** It is `Now That's What I Call Music! -
Topic` (`NYROuqKLoCk`) — a genuine compilation-label Topic channel whose upload is
hand-described (`Title: / Artist: / Album:`) rather than auto-generated, and which is not
premium. So the `- Topic` heuristic fails on *real* Topic channels carrying non-art-track
uploads. The description marker correctly declines to fire on it.

## What would actually settle it: the Song/Video link

YouTube Music's player has a **Song/Video toggle**, and which side is available (or greyed
out) is a direct statement about whether a canonical track exists for a given video. That is
the signal worth having, and it would allow *correcting* a bad queue entry rather than merely
flagging it.

**It is not in the YouTube Data API.** `videos.list` exposes no counterpart or track-entity
link at any `part`.

**It is in InnerTube, but not without a session.** `POST music.youtube.com/youtubei/v1/next`
with the `WEB_REMIX` client returns HTTP 200 unauthenticated, and the response carries the
Up next / Lyrics / Comments / Related tabs — but **no `counterpart` key at all**, with or
without `isAudioOnly` and `enablePersistentPlaylistPanel`. The pairing appears to require a
signed-in session.

So the cost of that path is: an undocumented endpoint that can change without notice, plus
cookies — the same authentication burden as yt-dlp, with none of yt-dlp's maintenance behind
it. Deliberately not built. If certainty is ever needed per-item, asking yt-dlp is the
cheaper and more honest option, and StemForge already does exactly that at the moment it
matters.

## Rejected alternatives

- **`- Topic` channel title.** One false positive, and misleading to verify by eye: YouTube's
  UI attributes art tracks to the *official artist channel* while the API still reports the
  Topic channel. The screenshot that prompted this work showed `corneliusofficial`, but
  `videos.list` for the same video (`Wsk3rBhYqoc`) returns `Cornelius - Topic`. The
  description marker sidesteps the discrepancy.
- **`categoryId`, `topicDetails`, `licensedContent`.** All high-recall, low-precision. A
  warning that fires on 88–103 healthy tracks would be ignored within a week.
- **Shelling out to yt-dlp.** Unnecessary given the above, and it would need cookies, a
  subprocess, and seconds per item.

## When to re-measure

The marker is a YouTube presentation detail, not a contract. If YouTube restyles
auto-generated descriptions, this silently degrades to "everything looks like a video
upload" — noisy, but never wrong in the dangerous direction. Re-run the join in
`V:\Repos\Yt-dlp_Formats` against `analysis/per-video.csv` to check.
